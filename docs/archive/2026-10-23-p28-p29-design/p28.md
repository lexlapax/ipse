# P28 brief: operator usability and release readiness

Proposal record, 2026-10-23, written against `dd510a7`. See the
[brief index](index.md) for conventions and baseline checks, and the
[plan](../../plan.md#p28-operator-usability-and-release-readiness) for scope.

## Goal and boundaries

A new operator should be able to install a tagged release and choose a provider
explicitly. They should be able to diagnose their environment, complete a first
real task and recover from common errors using only the manual and the CLI's own
messages.

Out of scope:
- new providers (P29) and decision engines (P30);
- code signing and notarization;
- package-manager distribution;
- Windows;
- a full-screen terminal UI;
- changes to approval, journal or sandbox semantics.

## Current state the packages build on

- **CLI.** `Ipse.CLI.run/1` (`lib/ipse/cli.ex:15-83`) parses one global strict
  option list and routes through `dispatch/2` clauses (`:85-299`). The exit codes
  are 0 and 1. `report/1` and `format_error/1` (`:524-550`) map only four atoms and
  otherwise print `inspect(reason)`. Help is the `@help` heredoc in
  `lib/ipse/cli/terminal.ex:59`. Use `Terminal.puts/2` for any value that may
  contain control characters.
- **Configuration.** `Ipse.Config.resolve/4` (`lib/ipse/config.ex:30-172`):
  - It reads JSON from `--config`, then `IPSE_CONFIG`, then `$IPSE_HOME/config.json`
    (`:302-310`). Trusted project files are `.ipse/config.json` (`:312-324`).
  - It tracks per-key provenance and a fingerprint.
  - The built-in default provider is `chatgpt` (`:9`), so a missing config silently
    means the ChatGPT subscription.
  - No code writes configuration. Readers do not check file modes
    (`read_source`, `:341-373`).
- **Credentials.** `credential/1` in `cli.ex:455-465` reads `OPENAI_API_KEY` or
  `ANTHROPIC_API_KEY`, or calls `Ipse.Auth.token/1`. `token/1` can refresh over the
  network. `Ipse.Auth.status/1` (`lib/ipse/auth.ex:149-162`) reads the protected
  file without network access. `ipse status` prints `inspect(map)` rather than
  JSON. The owner-only atomic writer pattern is `Ipse.Auth.write_credentials/2`
  (`auth.ex:769-794`).
- **Diagnostics to reuse:**
  - `Ipse.Tools.Sandbox.resolve/2` and `info/1`
    (`lib/ipse/tools/sandbox.ex:22-64`);
  - `Ipse.Runner.native_helper/1` (`lib/ipse/runner.ex:17-31`);
  - `Ipse.Journal.list/1` and `header/2` (`lib/ipse/journal.ex:83-158`);
  - `Ipse.MCP.Config.load/1` (`lib/ipse/mcp/config.ex:21-44`);
  - `Ipse.Extension.Registry.builtins/0` and `manifests/1`;
  - `Ipse.Config.manifest/1`.
  - Landlock support is checked only when a sandboxed command starts
    (`native/ipse-linux-sandbox.rs:366-368`).
- **Version.** It is written by hand in `mix.exs:7` (`0.1.0`), `dev/package.sh:39`
  (archive name) and `terminal.ex:60` ("Ipse 0.1"). The runtime reads
  `Application.spec(:ipse, :vsn)`.
- **Packaging and release:**
  - `dev/package.sh` builds `dist/ipse-0.1.0-OS-ARCH[-ABI].tar.gz` with no checksum.
  - `dev/release-launcher.sh` resolves its own directory from `$0` without following
    symlinks, so a symlinked `~/.local/bin/ipse` would look for the release in the
    wrong directory.
  - CI (`.github/workflows/ci.yml`) has no tag or release job.
  - No Git tags exist. No install, upgrade or uninstall procedure exists, and there
    is no macOS install chapter.
- **Upgrades.** Saved sessions do not store the Ipse version. Selected extension
  identity includes `host_sha256` over every host BEAM
  (`lib/ipse/extension/registry.ex:397, 565-591`). Any new build therefore refuses
  to resume sessions with extensions selected and returns
  `:resume_configuration_mismatch`. Sessions without extensions resume when their
  configuration matches.
- **Tests.**
  - `test/test_helper.exs` isolates `HOME` and `IPSE_HOME`.
  - `test/ipse/cli_test.exs` has an `IOFixture` for interactive input (`:1-70`) and
    fake loopback servers (`:74-84`).
  - `test/ipse/config/integration_test.exs` shows how to test a JSON-emitting CLI
    command.

## Decisions

- **D1, built-in default provider.**
  - Option (a) keeps `chatgpt` as the built-in default for compatibility. When the
    provider's provenance is the built-in default, `ipse chat` and `ipse run`
    print one stderr notice: `Using built-in provider default chatgpt (ChatGPT
    subscription). Run ipse setup to choose explicitly.`
  - Option (b) refuses to start without an explicit provider. This breaks existing
    scripts.
  - **Recommend (a).**
- **D2, first release version.** Tag the first release `v0.1.0`, since nothing has
  been released. Bump to `0.2.0` only if you want the tag to mark the P28 changes.
  **Recommend `v0.1.0`**.
- **D3, release workflow dependency.** A tag workflow that drafts a GitHub Release
  uses the `gh` CLI preinstalled on GitHub-hosted runners, or a pinned release
  action. Either is a CI dependency and needs approval recorded in
  [dependencies](../../developer/dependencies.md#ci-inventory).
  **Recommend preinstalled `gh` with the default `GITHUB_TOKEN`.** It adds no
  third-party action, and the release stays a draft until a human publishes it.

## WP1: one version source and `ipse --version`

Purpose: remove the hand-copied version strings and give operators and bug
reports an exact build identity.

Changes:
- Add `Ipse.version/0` returning `Application.spec(:ipse, :vsn) |> to_string()`.
  Add `Ipse.build_info/0` returning a map with these keys:
  - `version`;
  - `otp_release` (`:erlang.system_info(:otp_release)`);
  - `elixir` (`System.version()`);
  - `os` and `arch`, using the same detection as `dev/package.sh`;
  - `commit`.
- Embed `commit` at compile time from `IPSE_BUILD_COMMIT`. Set that variable in
  `dev/build.sh` and `dev/package.sh` from `git rev-parse HEAD` when Git metadata
  exists. Otherwise it is `nil`. Never shell out at runtime.
- `terminal.ex:60` interpolates the version. `ipse --version` and
  `ipse version [--json]` print it, the latter with `build_info/0`.
- `dev/package.sh` reads the version from `mix.exs` (for example
  `mix run --no-start -e 'IO.write(Mix.Project.config()[:version])'`, or a grep
  with a clear failure) instead of hardcoding `0.1.0`.

Tests:
- A CLI test for `--version` and `version --json` keys.
- A package test that the archive name contains the `mix.exs` version.

Done: version appears once in source (`mix.exs`). Baseline checks pass, plus
package and installed verifier.

## WP2: actionable errors and refusals

Purpose: every operator-visible error says what failed, whether an effect may have
happened and the next command. This package lands before `doctor` and `setup` so
they reuse the same messages.

Changes:
- Create `Ipse.CLI.Errors` in `lib/ipse/cli/errors.ex`. Its `message/1` maps a
  reason to `%{text, recovery}`, where `recovery` is a manual anchor such as
  `docs/operator/recovery.md#...`. `format_error/1` in `cli.ex` delegates to it.
  Unknown reasons print `Unexpected error (CODE). See docs/operator/recovery.md.`,
  where `CODE` is a short stable atom name or the exception module. Never print
  `inspect/1` of arbitrary terms, which may contain paths or values.
- Cover at least the atoms the survey found surfacing raw:
  - `:invalid_session` (`session.ex:2400`);
  - `:workspace_not_found` (`:343`);
  - `:invalid_provider_endpoint` (`:2410`);
  - `:invalid_journal`;
  - the existing four in `format_error/1`.
- Replace these vague strings with specific ones that keep their redaction:
  - "Session could not be loaded." (`cli.ex:510`). Distinguish missing, locked,
    malformed and incompatible.
  - "Invalid configuration workspace." (`config.ex:170`).
  - "Invalid profile or role configuration." (`profiles.ex:30`). Name the profile
    and the failing field, not its value.
  - The MCP catch-all (`mcp/config.ex:38-43`). Name the server and the failing
    field class (for example command, url, env or headers) without values.
- `ipse status` prints JSON (`Jason.encode!(..., pretty: true)`) with the same keys
  `Auth.status/1` returns.
- Grep every `{:error, "` string reachable from the CLI. Make each one name the
  next step or point to `recovery.md`. Add the missing recovery table rows to
  [recovery](../../operator/recovery.md).

Tests:
- A table-driven test over `Ipse.CLI.Errors.message/1` for every mapped reason.
  Assert that the text contains no `%{`, `#PID`, absolute home paths or
  credential-like values.
- Update existing CLI tests whose expected text changes. Do not loosen any
  assertion to a substring that would also match the old vague text.

Done: no CLI path prints `inspect(reason)`. Recovery rows exist for each mapped
reason. Baseline checks pass.

## WP3: `ipse doctor`

Purpose: one command that explains whether this machine and configuration are
ready, without network access unless the operator asks for it.

Interface:
- `ipse doctor [--json] [--cwd PATH] [--config PATH] [--profile NAME] [--probe-provider]`.
- The command accepts the same configuration options as `ipse config`, so it
  diagnoses the configuration the operator will actually run.
- It exits 0 when no check is `fail` and 1 otherwise.

Each check is a map with these keys:
- `id`: stable dotted name;
- `status`: `ok`, `warn`, `fail` or `skip`;
- `summary`: one line, no secrets;
- `detail`: optional;
- `recovery`: a command or manual anchor.

Human output is an aligned table through `Terminal.puts/2`. `--json` prints
`%{"version" => 1, "build" => build_info, "checks" => [...]}`.

Checks, in order:

| id | Source to reuse | Rule |
| --- | --- | --- |
| `runtime.build` | `Ipse.build_info/0` | Always `ok`; reports version, OTP, Elixir, OS and arch |
| `home.layout` | `cli.ex:516-519` path helpers, `File.lstat` | `IPSE_HOME`, `auth/` and `sessions/` are directories owned by the current user. Group/other-writable is `fail`; group/other-readable `auth/` is `fail`; missing is `ok` with "created on first use" |
| `config.files` | `Config.resolve/4` sources | Each source path, its trust status and parse result. Operator config that is group/other-writable is `warn`, and group/other-readable is `warn` |
| `config.provider` | Config provenance | `ok` when explicit; `warn` (D1) when it comes from the built-in default. Shows provider, model and billing mode (`Ipse.Usage.billing_mode/1`) |
| `credentials.selected` | `Profiles` credential map, `Auth.status/1` | For each provider used by the selected profile and roles: env var present and non-empty (never print a length or prefix), or ChatGPT file present, owner-only and unexpired. **Never call `Auth.token/1`**, because it may refresh over the network |
| `sandbox.native` | `Sandbox.resolve(:native, cwd)`, `Runner.native_helper/1` | `ok` when helper checks pass; `skip` on unsupported platforms; `warn` on macOS (experimental, matching the manual). Reports the requested policy, not enforcement; see WP3b |
| `mcp.config` | `MCP.Config.load/1` | Valid/invalid and server count; never launches a server |
| `extensions.selection` | `Config.runtime/2` registry prepare | Selected IDs and whether their artifacts verify, without starting workers |
| `sessions.store` | `Journal.list/1`, `header/2` | Count, unreadable or oversized headers and directory mode. **Never acquire or test session locks**, because that would race a starting session |
| `provider.reachability` | Only with `--probe-provider` | See below; otherwise `skip` with "pass --probe-provider" |

Provider probe:
- It sends one bounded `GET` per selected provider through the existing private
  Finch client (`Ipse.HTTP`), with TLS verification on and a 10-second total
  deadline. No inference request is sent.
- Probe targets:
  - Ollama: `GET {base}/api/tags`.
  - OpenAI: `GET {base}/models` with the API key.
  - Anthropic: `GET {base}/v1/models` with headers matching `anthropic.ex:16-20`.
  - ChatGPT: `skip` with "subscription reachability is verified by a real
    session". Do not call private endpoints.
- Map 401 and 403 to a credential failure, connection errors to reachability,
  and 2xx to `ok`. Response bodies are discarded after the status is read.

WP3b, optional native probe:
- Add a `--probe` mode to the Linux sandbox helper. It reports the Landlock ABI and
  whether the required namespaces can be created, without executing any command.
  Doctor then reports `sandbox.native` as enforceable or not.
- Decide after WP3: if the helper change touches more than the probe path, defer
  it and keep the policy-only report.
- Tests: native-tagged Linux tests, plus a refusal test on macOS.

Tests:
- One `test/ipse/cli/doctor_test.exs` case per check status, using temporary homes,
  file modes and fixture configs.
- A no-network test: start a loopback listener, configure it as the provider base
  URL, run `doctor` without `--probe-provider`, and `refute_receive` any connection.
- With `--probe-provider`, the same listener receives exactly one `GET`.
- The JSON shape test asserts `version` and stable ids.
- A test that `credentials.selected` never contains the synthetic key value.

Done: doctor runs from source and from the installed archive (add it to the
installed verifier). Operator docs have a "Diagnose your setup" section.
Baseline checks pass.

## WP4: guided `ipse setup`

Purpose: an explicit first-run choice of provider, billing, model and defaults,
written to an owner-only operator configuration file after the operator sees it.

Interface:
- `ipse setup` is interactive and requires a TTY. Without one, it refuses with
  instructions to use flags.
- `ipse setup --provider P --model M [--sandbox off|native] [--write]` is
  non-interactive. Without `--write`, it prints the would-be file and exits 0.
- The target path is the operator config path from `config.ex:302-310`.

Flow:
1. Read and parse existing configuration. If the target exists, print its path and
   effective provider, then stop. `--replace` writes a timestamped backup
   (`config.json.bak-YYYYMMDDTHHMMSSZ`, owner-only) and replaces only the
   `settings` keys setup owns. It preserves every other top-level key byte-for-byte
   through decode/encode with the same values.
2. List providers with billing labels: ChatGPT subscription, OpenAI API (billed),
   Anthropic API (billed), Ollama (local) and demo (no model). No option is
   preselected. An empty answer re-asks.
3. Show the default model for the chosen provider (`config.ex:18-24`) and accept an
   override validated by `Ipse.Provider.model_name/1`.
4. Credential step:
   - Show where the credential comes from: env var name, `ipse login` for
     ChatGPT, or none.
   - Never read, echo, store or offer to store an API key.
   - For ChatGPT, offer to run the existing `ipse login` flow only after an
     explicit yes.
5. On Linux, offer `sandbox: native` only when `sandbox.native` is `ok`.
   Otherwise explain why it is unavailable.
6. Print the exact JSON to be written, `{"version": 1, "settings": {...}}`, and ask
   for `write` to confirm. Reuse the approval-code style only if it stays simple;
   a typed word is enough here because the action is local and reversible.
7. Write with a new shared helper `Ipse.PrivateFile.write_atomic/2`, generalized
   from `Auth.write_credentials/2`: exclusive temp file, chmod 600, fsync, rename,
   and the directory created 700. Then switch `Auth` to the helper with unchanged
   behavior and messages.
8. Re-resolve the written configuration and run the doctor checks except the
   provider probe. Print the summary and the next command (`ipse demo` or
   `ipse chat`).

Tests:
- Use `IOFixture` for interactive flows. Cover:
  - refusal when the target exists;
  - `--replace` backup and preservation of unrelated keys;
  - an empty answer re-asks;
  - a non-TTY refusal;
  - a dry run without `--write` changes no files;
  - modes 600 and 700;
  - no credential value appears in output or file;
  - the written file resolves with `config.provider` provenance from the
    operator file;
  - the D1 notice disappears after setup.
- `Auth` credential tests still pass unchanged.

Done: a fresh `IPSE_HOME` goes setup, then doctor all `ok` or explained `skip`,
then demo, from source and the installed archive. Baseline checks pass.

## WP5: tagged release, checksums and install lifecycle

Purpose: a versioned, verifiable download with documented install, upgrade and
uninstall.

Changes:
- `dev/package.sh` writes `ARCHIVE.sha256` beside the archive, in `sha256sum`
  output format. Use `sha256sum` on Linux and `shasum -a 256` on macOS, failing
  clearly if neither exists. The installed verifier checks the sidecar.
- `dev/release-launcher.sh` resolves symlinks before computing `IPSE_RELEASE`. Use
  a portable POSIX loop over `readlink`, because macOS lacks `readlink -f`. Keep
  `IPSE_WORKSPACE=$PWD`. Add an installed-verifier case that runs the launcher
  through a symlink in another directory.
- `.github/workflows/release.yml` triggers on `push` tags `v*`. It reuses the
  `ci.yml` matrix steps for build, package and installed verification. Then it
  creates a **draft** GitHub Release with `gh release create --draft`, attaching
  every archive and `.sha256`. The workflow body comes from
  `docs/releases/vVERSION.md`, and the workflow fails if that file or the
  version/tag match is missing. Pin action SHAs as `ci.yml` does, and record D3 in
  the dependency inventory.
- `docs/releases/v0.1.0.md` holds release notes. It covers what is supported,
  verified platforms, the accepted limits linked to the manual and the upgrade
  notes. Add `docs/releases/` to [the documentation map](../../index.md).
- `docs/operator/install.md` is a new chapter covering:
  - download;
  - checksum verification;
  - extraction to `~/.local/opt/ipse-VERSION`;
  - the symlink `~/.local/bin/ipse`;
  - macOS quarantine for unsigned archives (`xattr -d com.apple.quarantine`, with
    the trust implication stated);
  - first run (`ipse setup`, `ipse doctor`, `ipse demo`);
  - upgrade by installing side by side and switching the symlink;
  - uninstall, which removes the release directory and symlink and keeps
    `~/.ipse` unless the operator deletes it, with the consequences stated.
- Move the bundled-release part of `docs/operator/arch-linux.md:7` into the new
  chapter and link it from there.
- Upgrade guidance must state the actual behavior. Sessions with selected
  extensions refuse to resume on a different build. Finish them, export a handoff
  (`ipse handoff --resume ID --note TEXT`), or keep the previous release directory
  and resume with it. Sessions without extensions resume when configuration
  matches. Test the claim; do not just assert it.

Tests:
- Package tests for the checksum sidecar and symlinked launcher.
- An upgrade check in the installed verifier:
  1. Create a demo session with a built-in extension selected, plus one without.
  2. Rebuild from a temporary copy with a changed host BEAM, using a test-only
     module change in the copy, never in the repository.
  3. Assert refusal with the documented message for the first session and
     successful resume for the second.
  - If this is too slow for CI, run it locally and record the result in the
    release notes' verification section.

Done:
- a pushed `v0.1.0-rc.1` tag produces a draft release with Linux and macOS archives
  and checksums;
- installed verification passes on both hosted platforms;
- the draft is deleted after inspection;
- the real tag waits for WP6.
