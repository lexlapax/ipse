# Private full-facts management display candidate — 2026-10-29

This is a Linux-only, display-only implementation candidate. It does not accept operator input, construct a Review permit, consume consent, publish or forget anything, and no public or worker route invokes it. All management and protected-output gates remain closed. The [plan](../../plan.md) owns acceptance; [the management purpose](management-display-scope.md) and [independently reviewed journal/control prerequisite](management-share-controls-independent-review.md) define the scope. Further review and the actual input/effect journey remain necessary.

The private candidate resolves the existing project and selected bundled recipe, snapshots the existing management epoch, and creates its management journal using the original share-capable header owner. Its actual tracked journal-effect peer enters Identity → exact existing management Consent → authenticated Collection in that order. The live callbacks retain their original native Transaction stack while `ManagedLifecycle.prepare/3` derives the complete selected literal, signed metadata, root and operation facts. The same-owner stack is checked against the live Identity marker and exact Consent and Collection capabilities, so the four manifest positions are the actual management journal, Identity, Consent and Collection descriptions. No Session/Host identity or synthetic sender substitutes for the two actual management owner processes.

The private renderer reuses the complete existing Review facts, pretty JSON and challenge text; it adds a timestamped label saying whether the signed deadline had elapsed and that original source availability and current-use eligibility were not checked. It rejects a complete rendering over the existing 65,536-byte Review bound. This is faithful management inspection and does not turn expired evidence into eligible recall, capture or endorsement. The challenge on this test-only display is not read or accepted and cannot mint a permit.

The journal Writer drains and freezes before export. Both actual CLI and journal-owner EOF controls and the four retained descriptions are transferred to the matched native tty guardian/reader. The exact operation, complete immutable payload, both owners, each lease identity and destination are repeated at activation. The reader writes directly to the tty, never through BEAM output forwarding. D is write progress only. After reader reap, guardian lease drop and each native exporter settlement, C is observed; a separate operation-bound U releases the retained owner peers. Both actual control senders must exit cleanly before the journal Writer thaws. The nested Collection, Consent and Identity callbacks recheck and release their own owners before the private caller receives `{:closed, {:ok, receipt}}`; this receipt contains facts/display digests and is not a Review or mutation receipt. Any interruption, partial or late reply is unknown. Buffered terminal bytes cannot be recalled; an already admitted syscall may complete after owner loss while its descriptions remain held.

The original 120-second wall and monotonic operation budgets are captured at candidate entry. The current private five-second sender/setup budget only narrows them. In v5 native mode, the guardian first reports its Linux monotonic clock; the host combines that earlier sample with its remaining original monotonic budget, making a conservative absolute native deadline. The guardian maps it to an `Instant` using an earlier instant sample and rounded-up native time, and narrows its own timeout before activation. Both the native monotonic deadline and wall expiry are checked before every new bounded tty/status write. Slow synchronous preparation and syscalls are not hard-preempted; missing or late completion is unknown. The earlier relative-time native mode is retained only as historical evidence and does not establish this common deadline.
