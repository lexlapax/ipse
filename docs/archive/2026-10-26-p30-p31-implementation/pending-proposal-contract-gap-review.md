# Pending proposal acceptance and management: contract gap review — 2026-10-29

This read-only design review maps the frozen [baseline](baseline.md#confirming-a-proposed-decision)
and [contracts](contracts.md#origin-proposals-and-draft-intent) to current source.
It is not implementation or acceptance of P31E. No model, native test, aggregate
suite or held-out data was run. Existing publication and review gates remain as-is.

| Requirement | Current reusable pieces and concrete gap | Required increment and focused controls |
| --- | --- | --- |
| Pending identity, text and provenance | `Knowledge.Records.capture/4` creates a v1 `pending.` value with ID derived from lineage and exact text, `state`, text, category, reason, event/creation/expiry times and one original source proof. `ManagedRecipe` rederives identity and verifies the proof against host-authenticated members. This schema's `version` is a **format**, not an edit revision. Changing text currently changes the ID; there is no versioned edit journey. Source proof-shaped JSON alone is not authority. | Bind the host's exact namespace, key, current Collection revision, physical value hash, lineage and text hash at each step. Decide explicit correction/version semantics without silently changing old IDs. Validate and preserve source class/receipt, and refuse unavailable or changed evidence. Test same text/different source, same source/corrected text, stale revision, forged source and legacy v1 records. |
| Ordinary assistant suggestion without prior evidence | Existing capture requires a source handle and quote and `Records.proof?/1` accepts a bounded receipt-backed original/answer/outcome. There is no independently created host-assigned pending card for a new suggestion without prior supporting facts. | Add a narrowly typed host-observed assistant-proposal source or comparable exact completed-reply evidence, without inventing corroboration or trusting worker-selected origin. Apply exclusions before durable copying; do not require an earlier decision. Test unsupported suggestion, exact text, malformed/excluded content and no active recall on creation. |
| Explicit native acceptance | `Runner.Review` supplies real terminal display/input and same-owner one-use review permits; `Session.Input`, `DraftAcceptance` and `OperatorAssertion` contain useful observation and replay patterns. They do not implement this proposal journey. `OperatorAssertion` records the operator's own statement using `remember CODE` and changes origin; converting a pending source into that event would falsify provenance. | Add a distinct host-owned proposal render and accepted-decision event, bound to project, chat Session or fresh standalone client, exact ID/version/text hash, storage revision, render revision, full displayed bytes and fresh `accept CODE` observation. Journal the event separately while retaining original proof/origin. Acceptance establishes a decision, not objective truth or effect authority. Re-render, edit, interruption, expiry and revocation invalidate the code. Test bare yes, unseen card, piped/argv/`--yes`, cross-client/Session/project/version, duplicate event, resumed fresh render and native display failure. |
| Bounded displayed batch | `Runner.Review` can display host facts, but its generic size ceilings do not enforce this proposal's batch contract or select among cards. | Limit each fully displayed selected batch to eight items and 8 KiB, with immutable manifest hash and individual exact selection; no unseen accept-all. A batch can accept fewer items than displayed. Verify UTF-8 and actual escaped terminal/display bytes and frame limits. Test boundary, oversize, display truncation and selection of an unseen member. |
| Consent and atomic publication | `SemanticAdmission` and protected consent check current identity, policy, mode and effect at existing boundaries; `NormalizerV3.normalize` admits proposal as `never_current`. Its literal path requires exact strong-source proof, and current note metadata/recipe has no accepted-proposal semantics. An acceptance receipt or JSON schema cannot itself authorize writing. | Add a separately reviewed, narrowly typed host path that authenticates the real native event and original source, rechecks exclusions, current active consent, current candidate/version and expiry at the publication boundary, then atomically records the linked acceptance and resulting state with one-use operation identity. No worker-supplied receipt, direct Core bypass, promotion to `native_operator_assertion`, truth claim or permission grant. Resolve or inspect an interrupted/unknown commit without auto-replay. Test revoked/disabled/expired consent, source change during review, double delivery, concurrent correction and cancellation/owner loss. |
| Standalone list, reject, forget and reduce while paused/disabled/revoked | `CLI.Knowledge.Management` starts no worker and owns protected journals, but handles `note.` targets only. `forget/3` and reviewed retention presently refuse at `native_review_publication_fence_unavailable`; expiry has a separate note/history path. `knowledge.ex` exposes no pending-review command. Neither existing management nor the extension's `note.` index is a pending-management journey. | Extend the existing protected management boundary with a **closed pending-only** bounded listing/JSON export and exact-target reducing operations under project/Collection identity and current state, independent of active publication consent and without worker/inference. Reuse lifecycle intent, operation inspection, native ownership, signed sidecars and CAS as appropriate; refuse unknown or unconfirmed cleanup. Test paused, disabled, revoked and absent grants; isolation; reject/forget/shorten without renewal, terminal/JSON listing, no worker/model, and races. Acceptance/publication stays gated by active consent. |
| Pending capacity and expiry | `PendingCapacity.check` reads at most 64 pending references under the held Collection normalizer and refuses 64 or more or physical total above 256 KiB; `NormalizerV3` supplies a host-controlled nonrenewable pending clock at most seven days and `never_current`. The worker's stored times are schema data and cannot replace the authenticated host deadline. `Knowledge` also scans on its capture path. | Count all actual pending/review items under the same protected lock, never silently evict, and visibly report expiration/refusal; use signed clock/sidecar when determining eligibility and prevent listing from renewing it. Include duplicate IDs, concurrent inserts, expired but unreclaimed values, exact byte limits and shortened policy in tests. |

The smallest independent domain-only candidate is a pure projection/validator
in `extensions/knowledge/src/knowledge/records.ex` with focused
`test/extensions/knowledge/knowledge_records_test.exs` cases. It can check the
closed v1 shape, rederive the current lineage/text ID, and expose text hash,
category, original proof and claimed times for inspection. It cannot establish
source authenticity or eligibility, mint codes or events, attach a host record
revision, mutate storage or make a candidate recallable. `Contracts` schemas
validate structure but do not enforce temporal relationships; the host's signed
pending clock and current record metadata remain authoritative. Existing
schema-valid values that do not meet stronger semantic checks should be
reported as invalid/unavailable, not silently repaired or promoted. Coordinate
this optional substrate with the extension producer before editing shared files.

Likely owners for the complete journey are the Knowledge records/contracts and
capture producer; a distinct Session proposal render/event and Saved replay
validation; native `Runner`/review ownership and input witness; Collection's
managed candidate/accepted-decision normalization and protected consent;
standalone `CLI.Knowledge.Management` plus CLI dispatch; and their corresponding
focused extension, Session, native and CLI tests. These are coordination points,
not permission to add a generic trusted-plugin engine or expose Core domain
mutation to arbitrary workers. The separately blocked native publication fence
and full end-to-end operator journey remain required.
