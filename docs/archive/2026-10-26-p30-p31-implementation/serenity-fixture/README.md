# Serenity device-fault fixture: review prototype

This directory contains a **disabled, unreviewed real-device prototype**, not an approved runnable fault test. `identity_guard.rs` has no commands, device access, mounts or cleanup code. It checks exact loop backing inode and filesystem major/minor, device major/minor, reference, zero offset and 512 MiB bound; exact mapper name, UUID, device and open count; and one exact whole-device linear or error table. Its mock state machine requires a pending record before each effect and refuses replay after interruption. Its `mock_fault_commands` illustrates the intended named-mapper switch but cannot execute it. `controller.rs`, `real_backend.rs`, `provisioning.rs`, `loop_device.rs`, `io_sentinel.rs` and `native_probe.exs` contain draft effect code, but no enabled entry point.

Compile/run the pure mock on any Linux host:

```sh
rustc --edition=2021 --test -D warnings identity_guard.rs -o /tmp/ipse-identity-guard-tests
/tmp/ipse-identity-guard-tests
```

The combined controller suite has 27 passing mock/safe-subprocess tests. Those values never address an actual host device; safe subprocess tests execute local `printf`, `head`, `sleep` and synthetic shell scripts in a fresh temporary directory. The native frame, loop-device encoding and sentinel mock tests also pass. No inference about kernel/profile qualification follows. `container_harness.sh` only renders a potential Docker command and never starts a container.

## Real controller integration still required

`provisioning.rs` and `real_backend.rs` now contain unreviewed, unconnected provisioning, fault and teardown code. The compiled `controller.rs` entry intentionally exits without invoking it. Its mock tests exercise ordering and selected command-capture behavior, not its interaction with loop, device-mapper, the container or Btrfs. The separate raw native probe is also disabled.

A reviewed controller must create a unique 0700 fixture directory; write an exclusive bounded 512 MiB backing file; record its device/inode; and obtain a specific loop with `--offset 0`, `--sizelimit 536870912` and an unpredictable `--loop-ref` matching the mapper nonce. Capture a **single** `losetup --list --raw --noheadings --output BACK-INO,BACK-MAJ:MIN,MAJ:MIN,OFFSET,SIZELIMIT,RO,REF DEVICE` observation and normalize its seven whitespace-separated fields into the mock guard's delimiter format. `losetup` here has no `--separator`; never concatenate individual command results as a purported atomic observation. Verify live tool output and supported options before use. The block node and dynamic device-cgroup rule must match the discovered loop number; their safe creation and lifecycle remain unimplemented.

Create a unique mapper UUID and name, verify one exact `linear` table referencing only the recorded loop and 1,048,576 sectors, then mount the newly formatted filesystem in the container's private namespace. Obtain `dmsetup info` for `name,uuid,major,minor,open` with a literal separator and an exact `dmsetup table` observation. Match both through fresh guard checks, plus `mountinfo`, loop backing identity and inode, immediately before every effect. These checks cannot prevent another root-capable host actor from changing global device state between observation and ioctl; independent review and appropriate exclusive coordination are required. Failure, extra targets, ambiguity or any mismatched object must stop the run without retry or destructive cleanup.

At a synchronized actual Ipse native-owner staging boundary, persist and fsync a unique fault-pending record. The proposed mapper change is `suspend --noflush --nolockfs NAME`, `reload NAME --table "0 1048576 error"`, then `resume NAME`; verify the exact UUID and active error table, and prove the expected write/fsync actually returned EIO. The [dmsetup manual](https://man7.org/linux/man-pages/man8/dmsetup.8.html) says `--nolockfs` suppresses the filesystem sync attempt; `--noflush` applies only to targets that support it and already mapped I/O may still be flushed. Consequently neither option proves dirty data remains at the desired boundary. Suspend behavior on mounted Btrfs, active versus inactive table reporting, interruption, whether the fault reaches the targeted write, and response under hanging I/O are **unverified**. A crash or ambiguous result at any step is unknown: preserve state and do not automatically rerun or blindly issue resume/reload.

Restoring the original linear table after an observed fault also needs a distinct durable pending record, exact identity/table checks, suspend/reload/resume and independent confirmation before observation or teardown. Restoring a failed Btrfs filesystem is not necessarily safe or sufficient for successful recovery; record fsync, mount, filesystem and transaction outcomes, including errors. Explicitly validate no default `dmsetup` behavior flushes/hangs or changes an unrelated mapping. Test ENOSPC separately on a bounded fresh filesystem, not by filling host storage.

Normal cleanup must separately confirm fixture-only process termination, unmount, mapper UUID/table and zero holders, mapper removal, loop backing identity and detachment. A crash-safe ledger and identity-safe recovery need to be implemented. No `remove_all`, `losetup -D`, unverified wildcard deletion or blind force. Inspect and retain artifacts if any cleanup check fails. The mock's state transitions model the ordering but are not a durable ledger or an operational cleanup implementation.

No project dependency was added here. Host `btrfs-progs`, `util-linux`, `device-mapper`, the Docker runtime/image and other non-Rust/Elixir test dependencies require the repository's explicit approval and inventory before being added as project tooling. A production test must also supply the actual native-protocol driver and independently audit fail-closed permission, memory, timeout and provenance controls; this mock is only a starting point.

## Independent review: unresolved stop conditions

The prototype remains disabled. A fresh preflight check followed by a journal fsync and subprocess launch is not an atomic identity-on-open operation; a host actor with root-equivalent access could replace a global loop or mapper during that gap. Docker/CAP_SYS_ADMIN is not an exclusion boundary. A credible trusted host-coordination and identity-at-effect argument is still required. The read-only staged tool/library mount must also have an attested immutable lifetime; hashing a writable pathname before execution does not prevent replacement. The same issue applies to hashing a raw helper then starting it by pathname.

The process-group survivor check is only a partial cleanup control: a descendant can escape its original process group. Require a separately observable container/cgroup lifetime, bounded confirmed shutdown and an unknown result if that proof fails. Current one shared deadline and 128-command counter can be exhausted before teardown; independently reserve bounded recovery resources, while preserving the rule that uncertainty does not authorize automatic compensation.

A loop's sysfs `holders` directory lists stacked block devices, not every open descriptor or mount in another namespace. A container-scoped `losetup` inventory might be incomplete. Thus an empty holders list plus a local list is not a proof of host-global nonuse or safe detach. The current cleanup prototype must not be enabled until this is addressed.

Raw native `U` error code 4 combines all I/O failures during staging; it does not reveal that the actual native operation returned EIO. The standalone sentinel distinguishes EIO only for its own write or fsync. Record these separately; a sentinel EIO plus native U4 is not proof of exact native errno. The raw probe also bypasses Ipse's Transaction supervisor and cannot establish supervised-owner cleanup. Actual supervised integration and exact fault timing remain unimplemented.

The prototype subsequently added an explicit, separate 30-second/32-command cleanup reservation only from a caller-supplied known restored state; the mock rejects reservation after unknown or a second reservation. This is not yet linked to a verified durable-state recovery flow, and does not prove that 32 operations or 30 seconds suffice. It must not be enabled as a workaround for unconfirmed device state.
