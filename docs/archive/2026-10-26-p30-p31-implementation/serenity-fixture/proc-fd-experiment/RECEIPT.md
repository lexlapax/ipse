# Proc FD identity experiment, 2026-10-27

This no-device synthetic experiment checks what a process FD-info snapshot can and cannot establish. The [source](proc_snapshot.rs), SHA-256 `08d6293557313c5730614bc021d3321bde711f5878d13fa6795660cf2fb352f9`, reads bounded `/proc/PID/fdinfo/N` inode, mount ID and flags and the process executable's device/inode. [Two tests](test-results.log) pass: close and different-file swap are detected; same-PID exec changes observed executable identity. A same-inode reopen with CLOEXEC restored deliberately produces the same FD-info tuple, demonstrating that matching fields do not establish the same open file description. An initial test failed because `dup2` cleared CLOEXEC; the corrected test explicitly restores it. The failed test's exact temporary files were removed after identity/content checks.

Upstream [Linux v7.2.11 proc FD implementation](https://raw.githubusercontent.com/gregkh/linux/v7.2.11/fs/proc/fd.c) reads FD information and may invoke a file operation's `show_fdinfo` callback. The exact running Arch kernel's source/binary parity and Btrfs callback behavior were not established; no claim is made that an FD-info or executable metadata check cannot touch or block on the faulted filesystem. This experiment neither establishes the sixth release failure nor qualifies the kernel, and does not authorize replay of that pending effect.
