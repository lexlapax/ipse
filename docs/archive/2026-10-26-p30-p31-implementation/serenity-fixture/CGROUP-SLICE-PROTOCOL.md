# Proposed retained-parent Docker cgroup observation

Status: proposed harmless experiment, **not executed or approved by an independent reviewer**. It must be reviewed before creating the slice. It exercises no block devices, mounts, filesystem faults, project directory or model service. It uses only the already approved Docker, pinned existing image and Elixir/Rust toolchain; it does not require `systemctl`, `systemd-run`, an image pull or package installation.

## Why the existing collector is not a direct wrapper

Ipse's existing `native/ipse-measure.rs` measures processes it creates with `clone3(CLONE_INTO_CGROUP)`, retains kill/event descriptors and has an independently anchored cleanup protocol. Starting `docker run` under that collector measures the Docker CLI, but the Docker daemon creates the container's processes in a separate systemd-managed scope. On Serenity Docker uses the systemd cgroup driver. The [Docker daemon documentation](https://docs.docker.com/reference/cli/dockerd/#default-cgroup-parent) says this driver's `--cgroup-parent` is a `.slice` name; the collector's existing private `ipse-run-*` cgroup is not such a slice. No claim that the current collector automatically owns the Docker population is justified. Running it *inside* a container would require independently verified cgroup delegation and an anchor outside its measured subtree; that has not been established.

## Exact harmless experiment

1. Generate a cryptographically random 32-lowercase-hex nonce. Compute the full parent unit name `system-ipsequal<nonce>.slice` and two full container names `ipse-anchor-<nonce>` and `ipse-workload-<nonce>`. Before action, verify each exact container name and prospective cgroup/slice path is absent; inability to query is unknown. Journal an exclusive, owner-only durable setup intent before creating anything. Never re-use a nonce. The slice-name-to-path mapping should be resolved from actual observed cgroup membership, not trusted solely from string construction.
2. Start the **anchor** from the pinned image using Docker `--pull never`, `--network none`, `--read-only`, `--cap-drop ALL`, `--security-opt no-new-privileges:true`, `--pids-limit 16`, `--memory 64m`, explicit unprivileged UID/GID and `--cgroup-parent system-ipsequal<nonce>.slice`; its only command is bounded `sleep`. No host devices, binds or project mounts. Keep the exact returned 64-hex Docker ID, confirm inspected ID/name/image/running state match the expected run, and confirm the process exists. Record PID *and start-time identity*, host `/proc/PID/cgroup`, and its exact cgroup child path. Discover the parent slice from that membership, retain an open parent directory FD and its device/inode, and require parent direct `cgroup.procs` is empty, parent `cgroup.events` is `populated 1`, and its only child cgroup is the expected anchor scope. Any extra child/process, path mismatch, missing identity or unreadable information is unknown; do not delete anything by name alone.
3. Start the **workload** under the same exact cgroup parent with the same restrictions and image. It runs a bounded shell that creates one `setsid` child and waits. Record exact Docker ID/name/image, init PID/start-time and both host `docker top` PIDs/PGIDs/SIDs. Verify the expected workload and anchor are the parent's only child scopes, workload `cgroup.events` is `populated 1`, and the parent still has no direct processes. Read the workload's `/proc/PID/status` and relevant `/proc/PID/mountinfo` fields, without logging environment or private data: require the expected unprivileged identity, no effective capabilities, `no_new_privs`, and all visible cgroup2 mounts read-only. Verify every observed workload process reports the exact workload cgroup; sample the anchor population and its member PID/start-time separately. If migration rights, alternate writable cgroup mounts or unexpected processes cannot be ruled out, classify the observation unknown.
4. Journal kill intent; invoke Docker kill/wait only for the exact previously verified workload ID. Verify its inspect status is stopped, then reread the retained parent directory and require the same device/inode and `populated 1` from the still-live anchor. Check the parent direct `cgroup.procs` is empty, its only remaining child cgroup is the exact anchor scope, and the anchor scope contains exactly the previously recorded anchor PID with the same start time and no nested cgroups. Recheck the exact workload scope is absent as one supporting observation, **not the sole proof**. Recheck `/proc` for the workload PIDs and compare their recorded start times; missing/reused identities are recorded accurately. The exclusion argument is contingent on the verified lack of workload cgroup-migration privilege and the trusted-host assumption: another root-equivalent host actor can move or create processes, and container `CAP_SYS_ADMIN` changes the argument. Any unconfirmed membership, nonempty unknown scope, failed read, unexpected migration, process identity ambiguity or inaccessible retained boundary is unknown, not a pass.
5. Only after recording the result, remove the stopped workload by exact ID after rechecking ID/name/image. Stop/wait and remove only the exact anchor ID after rechecking it. Confirm both container IDs are absent and the unique parent slice is empty/absent; if the slice persists or inspection fails, record an exact manual-recovery item. No wildcard removals, no `docker prune`, no stopping user services and no automatic force-removal of a device. If setup/kill times out or acknowledgement is missing, retain an unknown ledger and inspect the exact named resources before a manually initiated recovery; do not assume the effect was absent or replay it.

Every Docker command and the whole run need bounded output, a hard deadline and confirmed process/cgroup cleanup; `System.cmd` without such control is not sufficient. A crash-safe owner or independent guardian must retain cleanup authority and exact IDs. Prepare and independently test those mechanisms with mocks before running; no concrete executable implements this whole protocol yet.

## Limits

This tests only a harmless unprivileged Docker workload; it does **not** test block devices, mapper teardown, Btrfs, `CAP_SYS_ADMIN`, or actual Ipse Transaction behavior. The live fault container requires elevated capabilities for loop/mapper and mount setup, so a separate design must drop or tightly restrict capabilities before staging and prove cgroup migration is impossible during the relevant lifetime. A retained parent with one anchor does not alone prove cleanup. Passing this experiment cannot qualify 7.2.11 or replace the native profile/source review.

## Independent review additions

The first independent review requested additional fail-closed checks before this experiment can support any absence claim: compare the workload's user-namespace inode and complete UID mapping with the host's initial namespace; inspect cgroup DAC and *every* inherited FD, not merely visible mount paths; and establish the actual seccomp rules for `unshare`/user namespaces, `setns` and mount/remount. `Seccomp: 2` by itself says only that a filter exists, not what it permits. A conservative draft guard in `cgroup_guard.rs` rejects any observed cgroup2 descriptor and unknown descriptor filesystem, checks UID map/namespace, and requires filter mode, no effective caps and no-new-privileges. Its six mock tests pass, but it does not enumerate live descriptors or prove the filter content. A moving workload may change its descriptors between enumeration and use; a bounded exact-PID freeze or equivalent separately reviewed observation is needed. PID freeze/signal itself must avoid PID reuse and have a crash-safe thaw guardian.

The anchor and workload entrypoints, anchor deadline and liveness immediately before workload kill must be explicit. Compare the retained parent directory FD's device/inode with the current named parent at each check. An inherited writable cgroup FD, alternate writable cgroup mount, changed UID mapping, unknown seccomp policy, extra direct or child process, or failed identity check is unknown. No slice may be created until a concrete executable implements these checks and an independent reviewer accepts it.
