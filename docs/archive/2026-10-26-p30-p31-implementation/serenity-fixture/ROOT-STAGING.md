# Root-owned staging observation and cleanup

Recorded 2026-10-27 on Serenity. To evaluate tool lifetime without exposing host block devices, an offline pinned-image container with only `CAP_DAC_OVERRIDE`, no network and read-only root copied approved, already-installed tool/library files from a private temporary source to a new directory. The host staging root was `/tmp/ipse-serenity-root-stage.ApDy9s6A`, device 53, inode 57067, UID 1000, mode 0700. The root-owned `bin` and `lib` directories were device 53/inodes 57069 and 57075, UID 0, mode 0555. The [recorded identities](root-stage-identity.txt) SHA-256 is `1c0d4afb0c9b31b185de4931afe2ef31209e9d976994abdaa81720bf19b0a034`; [file hashes](root-stage-file-hashes.txt) SHA-256 is `a19f44e78c1b94ec0bb10d27c6ec0e0d624f238cfbe4b2a83184bcb586c29553`. All 21 files were root-owned, nlink 1, non-writable, and their bytes matched the preexisting inspected host manifest. A separate unprivileged, capability-dropped, offline read-only bind showed the same UID/mode/device/inode/nlink for a sampled binary and library inside and outside the bind. This is not an atomic proof for every file or protection from a host root/Docker-group actor, CAP_SYS_ADMIN remount, or changed dynamic loading.

The first cleanup attempt failed before deleting any file because the image lacks `cmp`; a follow-up host check confirmed the original three directory identities and all 21 files still existed. The second attempt used `set -eu`, rechecked exact stage/bin/lib identities, refused non-regular/unexpected entries, compared the count and per-file SHA-256 to the original private source, checked UID 0/nlink 1 for each file, removed only those named files and the two known directories, then rechecked the parent inode before `rmdir`. It completed with exit 0 and the original stage pathname absent. No host block devices were passed to either container. This cleanup applies only to that exact disposable stage, not to loop, mapper or mount recovery.
