## Preserve the pending decision boundary

The [frozen proposal contract](baseline.md#confirming-a-proposed-decision) offers
correction and invalidates earlier acceptance codes after an edit. A pending
candidate must keep its original headless/generated provenance and needs separate
fresh acceptance. Reusing literal supersession or treating edited text as a new
original interactive assertion would change that meaning.

`knowledge correct PENDING_KEY 'TEXT'` therefore displays an exact old/new request
under the existing native management owners and requires fresh `correct CODE`.
`PendingCorrection` preserves category, reason, proof, worker-recorded times and
signed first/deadline. The new text has a new candidate ID. One atomic request
deletes the old pending row, inserts the new pending row and retains an old-ID
correction/suppression marker linking the replacement. The shared source anchor
and other candidates remain unchanged; the advancing floor fences old backups.
The new candidate stays `never_current` until separate native acceptance.

Historical display uses the checked pending reader with active Consent and the
management journal. Original-source availability is independently checked after
input. Publication reacquires that original source, rechecks active policy,
exclusions, current installed selection and exact pin, then reproduces the facts
against the actual Collection root. An original SourceCard is retained for the
existing verified-source adapter; a shaped card or parsed intent grants no lease.

The new `NormalizerV3.correct_pending/3` verifies the signed old row and original
clocks, replacement constraints and current source policy, then plans two exact
live-row edits. Public CAS prerequisites were checked by Core before normalization.
It preserves the 32-read, five-sidecar, eight-total-change and existing byte bounds.
`PendingCapacity.replace/4` subtracts the exact old pending bytes before checking
the new value, so replacement can use a full queue without eviction.

Generic Collection publication remains closed for this kind. The typed host-only
entry claims the exact native permit/intent/request/normalization, binds the last
synced lifecycle intent through the existing Writer/journal lease, and attaches
the actual source lease to the same native transaction. Final admission uses the
minimum policy/pending/permit deadline. No Rust protocol, dependency, public SDK
permission, global quota or provider selection changes. This core change is
required for native input, protected signing and the final source/journal fence;
a worker cannot supply those authorities.

The caller settles measured `notes.capture` usage only after owner and journal
cleanup confirm. Cancellation/known refusal settle zero; uncertain work retains
its full reservation and never replays. Journal inspection derives the intended
replacement key even for an uncertain intent, without claiming presence or
acceptance. Legacy lifecycle output omits that field.
