# Review native notes, permission and retention

Use the standalone knowledge commands to select the bundled native notes tool
for a project. Setup imports the shipped artifact and saves a protected permission;
it does not start a model or change your provider configuration. The selected
tool becomes available in the **next new session**.

Choose the interaction that matches the source. `/remember` reviews a statement
you write yourself. An assistant can nominate an exact sentence in its completed
reply for a separate decision card. Other attributed text can be captured as a
pending proposal for later standalone review. Pending proposals stay out of
current-note recall until explicit acceptance succeeds. An authorized unattended
client can save an eligible typed host outcome under the knowledge-only grant.

Review, editing, retention and forgetting have standalone management procedures
below. Interactive chat also supports reviewed correction of an ordinary native
note and replacement of a current statement or preference. Protected capture and
later use need the supported Linux storage profile and their applicable current
source and permission checks. Reducing management and elapsed-policy reclamation
have the separate rules below. Full capture readiness remains false; these bounded
paths do not qualify automatic extraction quality, every source combination or
installed use.

As a temporary containment, a generic managed worker read cannot return a stored
value unless the selected current-literal recipe authenticates it. This includes
pending proposals, saved overrides and unrelated values in a managed collection;
a returned scan page containing one is refused as a whole. The separately
approved bundled shadow assessment below has a protected single-proposal read.
Metadata-only indexes remain available. Pending duplicate detection uses that metadata and does not
renew a proposal. A capture that needs an existing override may now be refused;
do not remove the override to make it proceed. Inspect the Session journal and
the existing note or proposal before new work, especially if an earlier effect
was uncertain. Standalone pending review uses its separate protected path.

First install or build Ipse and [save your provider choice](configuration.md#choose-and-save-a-provider).
Use a private Ipse home and an existing workspace. These commands use that saved
provider; provider/model overrides and `--yes` are refused during knowledge setup.
They require no separate embedding account or download.

Protected writes also require the current native
[allocation profile](../../native/README.md#publish-protected-state-through-its-lock-owner):
the reviewed Linux `7.2.10` Btrfs/tmpfs profile, or exact `7.2.11-arch1-1` on
x86_64 with qualified tmpfs features. Btrfs on the newer kernel and macOS remain
unsupported for these writes. Follow the [storage-location checks](arch-linux.md#check-protected-storage-admission)
for exact feature requirements. All protected locations must qualify; the
default Btrfs home on the newer kernel still refuses. Tmpfs is volatile and is
never selected silently as a storage remedy. Installation alone does not
establish this prerequisite.

## Review the project and exact permission

Run from a terminal with matching native input and display:

```sh
ipse knowledge enable --cwd /path/to/project
```

For a new identity, choose the displayed `repository CODE` or `folder CODE`.
Repository scope shares with reciprocally verified Git worktrees. Folder scope
covers only that canonical folder. A linked worktree needs its primary repository
admitted first; once the repository has an active project grant, a new session
can verify and join a reciprocal worktree. A copied repository or forged `.git`
pointer does not establish membership.

Read the full review, then enter its fresh `enable CODE`. The review identifies
the artifact, project, selected main route, source categories, retention, expiry
and finite daily allowances. It also warns when protected note saving is
unavailable in the current runtime; saving permission does not enable that
capability. Bare `yes`, an old code, piped text and command-line
approval flags cannot save the grant. Anything else cancels the review. Import
and project admission can already have occurred, but cancellation saves no new
permission.

The permission is tied to the reviewed artifact. If an upgrade changes that
artifact, check `ipse knowledge status --cwd /path/to/project` and complete a
fresh `enable` review when needed; an earlier grant does not silently transfer.

Keep the matching Ipse installation when upgrading protected permission data.
Inspection leaves older control files unchanged; a later successful authorized
write can save the newer format while preserving usage, operation IDs and
unresolved effects. Older Ipse versions may then refuse that file. Preserve the
original home and lock files, use the matching newer installation, and follow
[protected recovery](recovery.md#inspect-unconfirmed-protected-knowledge) if a
write is unconfirmed. Replacing the control file or deleting its history is not
a migration or a way to restore allowance.

The native preset permits reviewed statements, literal typed tool outcomes and
attributed pending proposals. Plain messages, quoted third-party reports, native
question answers and generated text remain pending candidates. An exact quotation
does not establish that you endorsed its claim or category. Saving any candidate
still requires the corresponding grant. Ordinary notes have a 90-day host
retention ceiling; pending proposals have seven days and never become current
merely because they quote a source. Reviewed current statements and preferences
can persist. The full permission review is authoritative for
the selected rules. It authorizes no secondary model calls or downloads. Main
conversation requests retain their ordinary route and resource accounting.
The reviewed native selection bounds each Main request to the smaller of your
configured timeout and 90 seconds. Requests on its registered route buffer
assistant text until the response passes completion checks, so text can appear
after upstream generation finishes. Review the displayed route and effective
timeout before enabling; setup does not enlarge a shorter configured timeout.

The saved permission records scope for chat and headless `run`; it cannot bypass
source, recipe, expiry or current publication checks. Model-selected source reads
check every selected source's provenance even when their starting dependency list
is empty. Their terminal previews withhold source arguments and result text;
authenticated content still enters the journal/model continuation. After a
confirmed capture, subsequent source reads can continue under fresh checks. Older
root metadata is explicitly historical and cannot establish that a stored note
is currently eligible. Full automatic-capture readiness remains limited as
described by status below.
Workspace writes, shell commands,
MCP and delegation keep their separate approval requirements. The grant expires
after one year and has daily limits of 100 operations, 2 MiB of input and 4 MiB of
output. A refusal or uncertain attempt may consume conservative allowance.

An extension already admitted to read the project's knowledge can inspect a
read-only saved-policy accounting observation. It carries its policy epoch and
observation time and leaves saved-policy charges unchanged. The counts include
unresolved saved effects across periods; they do not describe an endpoint's
separate service quarantine. Treat any reported remainder as advisory: another
operation can use it before your next action, and the host still applies current
permission, source and atomic reservation checks. This observation cannot renew
or reset the saved grant.

For an ordinary model proposal derived from protected native notes, the Linux
chat client can display the complete arguments under their current source and
policy owners. Wait for `approval>`, then enter the displayed `allow CODE` for
one attempt or `n` to deny it. This review offers no reusable session grant.
`/cancel` stops the turn and clears queued prompts; `/exit` also leaves chat.
The display owners release before you answer; Ipse checks the sources and
permission again before execution. A changed source or revoked permission can
therefore refuse a proposal that you approved.

This development-source path requires the matching native helper, original
source journals and a complete escaped display within 64 KiB. For an accepted
decision, keep its original committed management journal as well: the display
retains both original journals, then checks current authority again after your
answer. Nested action approvals use the same native review for supported shapes;
delegated proposals and unqualified nested displays remain unavailable.
An unavailable owner or unsupported display refuses before the
effect starts. Preserve the Session and inspect the refusal; saving knowledge
permission does not bypass these limits.

After successful setup, start a new conversation:

```sh
ipse knowledge status --cwd /path/to/project
ipse chat --cwd /path/to/project
```

In chat, `/ext` lists the admitted tool/command schemas. Listing capture does not
grant permission to every candidate. Generated prose and unattended input do not
become current notes merely by appearing in the conversation. The native selection can prepare bounded existing-note
context before requests, subject to the
source and route limits below. Proposal management and quality qualification
remain separate from permission setup. For the existing explicit note-management
workflow, follow [Memory](memory.md).

## Try a local shadow assessment

Ipse can ask a separately approved local decision service for shadow advice
about one eligible native literal note or pending proposal, or for a comparison
of current note packs with ordinary recall. Records must be eligible under the
same grant. Accepted decisions are not supported by the single-record
assessment. Set up an Ollama main
route and a System One-compatible decision service first; Ipse does not supply
either service. For example, adapt this complete private operator configuration
to the models and numeric loopback ports you actually run:

```json
{
  "version": 1,
  "profiles": {
    "main": {"provider": "ollama", "model": "your-main-model", "base_url": "http://127.0.0.1:11434"}
  },
  "roles": {"main": "main"},
  "decision_profiles": {
    "advice": {"operation": "decision", "provider": "system_one_compatible", "model": "your-decision-model", "service_id": "local-advice", "credential": "none", "base_url": "http://127.0.0.1:8080", "timeout_ms": 30000}
  },
  "inference_services": {
    "local-main": {"version": 1, "origins": ["http://127.0.0.1:11434"]},
    "local-advice": {"version": 1, "origins": ["http://127.0.0.1:8080"]}
  }
}
```

Save it as `/private/path/ipse-local.json`. This selects the main and advice
routes; it does not configure a separate answer helper. For an ordinary shadow
comparison, review at most two decision calls and 300 seconds in a native terminal:

```sh
ipse knowledge experiment advice 2 300 --config /private/path/ipse-local.json --no-project-config --cwd /path/to/project
```

To include a separate extension's one-shot answer route, prepare that extension
**before** reviewing the grant or capturing source notes. First obtain a compatible
artifact, [import, inspect, trust and select it](extensions.md#import-a-reviewed-artifact)
in the same operator file. Trust its actual manifest capabilities, including
`host.model` and the required invocation/host-action capabilities. The shipped
Knowledge presets have no `host.model`; this option neither adds it nor installs
an answer extension.

A source checkout supplies the generic [model-call example](../../examples/README.md#build-an-inert-extension).
Its documented `model-calls` build recipe produces a separately importable
`invoke.command`/`host.actions`/`host.model` artifact. It exercises explicit text
inference, not a ready-made protected-note answer service or matched comparison.
An answer extension must independently preserve the real inherited source union
and supported request/result contract. Do not paste recalled protected text into
an unrelated prompt to bypass those checks.

Define the extension's requested text profile in the existing `profiles` object,
with your explicit provider/model/endpoint and normal limits. For example, name
it `extract` when that is the extension's requested profile; follow the
[helper model configuration](configuration.md#allow-a-longer-extension-answer).
A profile definition alone grants no protected route. To review it together with
the shadow routes, use this command **instead of** the two-route command above:

```sh
ipse knowledge experiment advice 2 300 --helper-profile extract --config /private/path/ipse-local.json --no-project-config --cwd /path/to/project
```

This selects exactly `main`, `decision.create/advice` and
`model.complete/extract`. Inspect all three actual provider, model, endpoint,
billing and service identities in the native review. The option uses the named
existing profile; it never changes the main provider, chooses a fallback or
installs code. It is supported only by `knowledge experiment`; duplicate options,
missing profiles and unavailable routes refuse instead of silently omitting the
helper. Every helper call retains ordinary full native approval, current-source
checks and Usage/service accounting. `CALLS` counts decisions only, not main or
helper requests, and is not a monetary allowance. No helper effect is added to
Knowledge's decision or collection-read tool permissions.

Read the complete review and enter its fresh `experiment CODE`. After the grant
is saved, start a new Session with the same configuration:

```sh
ipse chat --config /private/path/ipse-local.json --no-project-config --cwd /path/to/project
```

The time limit begins
before the review and ends no later than the current UTC accounting period; an
expired review cannot be saved. The grant replaces the project's prior knowledge
permission: already-running Sessions pinned to it lose permission for later
knowledge effects. The grant does not change the main provider. It limits call count, not money:
a local endpoint can itself forward requests to a paid service, so check the
chosen service's costs. In the new chat, save a reviewed literal statement under
the shadow grant, then use `/exit` and start another chat with the same command.
For example:

```text
/remember ordinary The release checklist requires a migration audit.
/exit
```

Use `/ext` to inspect the selected tools in the fresh Session. Keep the saved
note's complete key, or ask the model to find it with the knowledge index tool,
then ask the model to assess that key:

```text
Use the knowledge assess tool on note.<64-hex-character-key>.
```

To assess a pending proposal instead, first create it under the shadow grant
through the main model's capture tool, as in [the pending-capture example](#save-your-own-reviewed-statement),
and keep the returned `pending.` key. Close its source chat with `/exit`. If you
need to find a key, list historical metadata in the same project and home:

```sh
ipse knowledge review --json --config /private/path/ipse-local.json --no-project-config --cwd /path/to/project
```

Start a new chat with the shadow configuration and ask:

```text
Use the knowledge assess tool on pending.<64-hex-character-key>.
```

The metadata list does not establish that a proposal or its source is still
eligible. Keep the original Session journal and lock files available; the
assessment rechecks the signed candidate, original source, grant and expiry.
It refuses when those checks cannot be completed. Only the separately reviewed
bundled shadow tool can use this protected proposal read.

Replace the placeholder with the actual key. `assess` is a model tool, not a
slash command; the model must choose to call it. Review and approve each decision
request separately. A successful tool result reports `assessed`, the selected key,
and an experimental advice choice. `keep_baseline` recommends retaining the
ordinary baseline; `defer_candidate` is a deferral option intended for ambiguity,
conflict or low durability. The result does not identify which concern applies.
These labels are for comparison only; neither changes or accepts the selected
record. A null choice with a
reason such as `low_probability` or `refusal` means no advice was selected.
The decision action is recorded in the Session journal. Advice does not authorize
another effect.

To compare note packs instead, use `/ext` to inspect `select_shadow`, then ask:

```text
Use the knowledge index to find the current note keys. With select_shadow,
compare two different packs named release and migration, each containing at most
four of those keys. Use the query: Which conditions must this release satisfy?
```

The model must choose the tool and supply actual returned keys. The experiment
reads the complete note set, with at most sixteen records, and checks its current
sources and context allocation. More records, incomplete reads or a changed
allocation refuse the comparison. A complete set that fits ordinary recall
makes no decision request. For an over-budget set, review the separate decision
request before allowing it.

A `selection_shadow` result reports the ordinary greedy baseline and an optional
advised pack. The baseline may contain more than four notes; each proposed pack
is limited to four. Advice changes neither stored notes nor the context supplied
to your main model. A missing candidate can mean refusal, insufficient confidence
or unavailable allowance; inspect its receipt. This comparison is experimental
and does not qualify a default retrieval strategy or model quality.

Large comparisons can return a `saved.result` receipt instead of inline data.
Use its actual `output_id` with the
[complete-result procedure](extensions.md#invoke-a-command-and-inspect-its-complete-result)
to inspect the baseline and candidate. The receipt itself contains no advice;
reading saved output does not establish that its original sources remain current.

A denied request sends no decision call. Work admitted before expiry may finish
sending later; an unknown outcome retains its reservation. After the experiment, restore the ordinary
selection through a fresh review:

```sh
ipse knowledge enable --config /private/path/ipse-local.json --no-project-config --cwd /path/to/project
```

The tested assessments start with a literal note or main-tool pending proposal
saved under this grant in a previous Session. Carrying a record captured under a
replaced grant into this experiment has not been qualified.
Automatic assessment immediately after a write in the same Session is not yet
supported. Synthetic local controls exercise this flow. An installed-package
fixture covers a prior-Session pending proposal. These controls do not establish
model quality, independent human use or paid-service readiness.

## Save your own reviewed statement

After enabling knowledge and starting a fresh chat in the same admitted project,
wait for the Session to be idle, then enter your own statement:

```text
/remember ordinary The release checklist requires a migration audit.
```

Choose `ordinary`, `preference` or `current` deliberately. Read the complete
statement, category and project/artifact scope at the native review. Enter exactly
the displayed `remember CODE` at `remember>`; anything else cancels. This confirms
your statement and category, not its external truth or permission for other
effects. The selected saved policy, original source and normalizer are checked
again before one new v3 record is admitted. Ordinary notes keep their original
90-day ceiling; the other categories follow the reviewed policy. This command
does not replace an existing note, change retention or perform a supersession.

The statement is limited to 1,024 UTF-8 bytes. Its complete encoded source proof
must also fit 2 KiB, so an escape-heavy statement can be refused even within the
text limit. Ipse does not truncate it to fit. The separate 6 KiB stored-value
ceiling is not a 6 KiB input allowance.

Wait for the final result. The native owner makes its final locked publication
decision under the earliest policy/source deadline; a switch admitted before
expiry may physically finish later. If confirmation or publication is uncertain,
preserve the Session journal and inspect actual storage before new work. Resume
does not repeat the statement review or publication, and `--yes` supplies no
shortcut. The separate [Memory](memory.md) workflow keeps its own authority.

Model-selected source lookups recheck the selected provenance and show only
status in terminal previews; authenticated content still enters the private
journal and model continuation. A capture can settle before delivery of its
result fails. Inspect the stored effect and Session journal after an error;
an error does not mean nothing was saved, and resume does not repeat capture.
General end-to-end automatic `run` capture remains unqualified.

When the main model queues a new pending proposal, distinguish queue room from
the saved daily allowance. The pending queue retains at most 64 records and
256 KiB, including expired proposals. A readable warning starts when the
projected queue reaches 52 records or 80% of its encoded-byte ceiling. A full
queue reports `pending_capacity` and pauses that new save. It does not evict
another proposal or remove a protected note or pin. Review unwanted proposals
through their normal management procedure before attempting new work.

Saved-allowance advice instead reports observed operations, input bytes and
output bytes. A near-limit notice warns at 80%; `saved_policy_budget` pauses a
new pending save when a required resource has no observed capacity. Unresolved
effects can retain charges across daily periods. These observations are
advisory: another operation can consume capacity, and nonzero capacity does not
guarantee that the final atomic reservation will admit the complete capture.
An exact existing proposal is detected before either check; it adds no new
capture and does not renew its deadline. Other refusals do not establish that
the budget was exhausted.

Inspect the permission, pending metadata and any printed uncertain operation
separately:

```sh
ipse knowledge status --cwd /path/to/project
ipse knowledge review --json --cwd /path/to/project
ipse knowledge operation OPERATION_ID --cwd /path/to/project
```

Do not delete control history or retry an unknown effect to restore allowance.
The normal source, permission and final publication checks still apply after
either kind of warning.

Eligible unattended input remains a pending proposal rather than an endorsed
fact. After native permission setup, a headless task can use the saved grant
without `--yes`, through either task arguments or standard input:

```sh
ipse run 'Record this as a pending proposal: prefer ISO dates in reports.' --cwd /path/to/project
printf '%s\n' 'Record this as a pending proposal: prefer ISO dates in reports.' | ipse run --cwd /path/to/project
```

Both task forms are unattended input. A permitted model-selected capture stores
an attributed pending proposal even if the model assigns a preference category;
it cannot create an endorsed preference from that task. Workspace writes and
shell commands remain denied under ordinary headless defaults. The saved grant
supplies no authority to run them. Keep the returned pending key for separate
native acceptance below. These development-source paths do not qualify model
capture quality, retention endurance or installed use. If a capture
reports an unknown outcome, inspect the Session
journal and stored state before attempting new work. Do not promote quoted
reports or unattended task text to endorsed facts.

Use native decision review to confirm a selected candidate. Its stored provenance
does not establish source freshness; display and publication check it again.

You can also ask the main model in a later chat turn to queue one of its earlier
suggestions, for example:

```text
Queue your previous suggestion as a pending proposal for my review. Use the
exact suggestion as its source.
```

If the model selects an eligible original reply and capture succeeds, the tool
result identifies the `pending.` key. If it does not, use the metadata list
below to inspect what was saved; do not assume the suggestion was captured or
accepted. Close the source conversation before standalone review. A synthetic
model control covers this path, but it does not establish that every model will
choose the capture tool or that the suggestion is useful or true.

Existing literal reads still require their signed record and original Session
source. Keep the original sessions directory and retained lock files. A copy
cannot substitute for an unavailable original. Historical endorsement establishes
recorded input, not independent truth or new publication permission.

## Review a proposed decision during chat

Enable the native knowledge selection, then start a new normal interactive chat
in the same project and private home. Use its saved provider configuration and
the supported Linux protected-storage profile. For example:

```sh
ipse knowledge enable --cwd /path/to/project
ipse chat --cwd /path/to/project
```

Ask for a recommendation and a decision card, for example:

```text
Recommend a release channel for this workspace. Nominate your exact recommendation
in the final reply as a decision for me to review.
```

The model must choose the nomination tool and include the same exact text once
in its completed reply. A nomination creates no note and accepts no decision. If the
host can authenticate that reply and capture succeeds, it opens the native card
without another user prompt. Read the complete candidate, category, reason,
source and proposed retention, then enter the displayed `accept CODE` at
`approval>`. Any other answer cancels. Acceptance records your decision about
the proposal; it establishes neither the premises' truth nor tool permission.

Keep the printed conversation, reservation and management-journal IDs. Ipse
stops the chat reader and confirms closure of the conversation before opening
the protected management review. It resumes the same saved conversation after
confirmed success or a known refusal. The provider, billing choice, workspace
and custom sessions directory stay pinned. Reopening uses the conversation's
confirmed current mode; leaving planning does not reapply its startup flag.
Session edit and shell
grants end during closure, including an initial `--accept-edits`. The current
approval policy still applies; an explicit `--yes` remains an ordinary approval
choice. Queued chat input is discarded.

Each completed nominated answer can attempt one automatic capture and review,
with at most 1,024 UTF-8
bytes of selected text and an available original reply of at most 8 KiB.
Ambiguous text, supplied references, unfinished replies, planning, request drafts,
presentation transforms and incompatible extension deliveries refuse the card.
Replies already dependent on protected recalled notes are outside this first path.
Native synthetic controls cover a normal interactive start and a chat started
with `--planning` that completes a witnessed `/plan exit` before nomination.
Planning itself cannot capture or accept this decision. The exit must return
to an allowed normal enclosing mode; a configured or inherited enclosing planning ceiling
cannot be bypassed by requesting a card.
Another completed answer in a later turn can nominate a separate proposal.
An interrupted attempt remains spent for its original answer; reopening the
conversation never repeats that capture. Normal replies remain available as
original sources. An unavailable card does not mean that its pending capture was absent. Inspect
pending metadata before new work. Headless input cannot accept a card.

After confirmed acceptance, continue in the resumed conversation and ask a
followup that uses the accepted decision. Ipse checks its current signed record,
original answer and separate acceptance journal before delivering it as a
protected reference. The earlier visible reply alone does not establish that
the decision remains current. Keep both original journals available. You can
also use `/exit` and start a fresh chat in the same project to retrieve it from
a separate conversation. Neither route supplies permission for another effect.

Unconfirmed reader cleanup, close, display, publication or reopening stops this
automatic interaction. Inspect the original conversation and `knowledge operation
ID` before continuing, as described in [recovery](recovery.md#inspect-unconfirmed-protected-knowledge).
Resume restores no live decision code or review handle and repeats no capture
or acceptance. After a known cancellation, close the chat with `/exit` and
explicitly resume it without an initial task to review its pending decision:

```sh
ipse chat --resume SESSION_ID --state-dir /private/path/sessions --cwd /path/to/project
```

Keep the original provider configuration, Ipse home and state directory. Before
the first `you>` prompt, Ipse prints `Checking pending decision review before
chat starts.` It checks the original source, current pending value, saved
permission and the outcomes of earlier review reservations. An eligible pending
proposal receives a new card and fresh code, with its original provenance and
pending identity. It is not captured again. The return to chat immediately after
a review does not reopen the card automatically.

Wait for `approval>` or `you>` before entering input. Ordinary chat input is not
armed during the startup check. A missing or uncertain earlier outcome stops
review and requires inspection; a known permission denial opens no card. A
still-pending candidate can also be selected through the standalone procedure
below after inspection. Neither path reuses an old code or reservation.

## Review a pending proposal

From the same admitted project and Ipse home, list one bounded page of pending
metadata:

```sh
ipse knowledge review --cwd /path/to/project --json
```

The result contains at most 32 keys with revisions, hashes and encoded sizes;
it contains no proposal text. If `next` is non-null, request another page with
`--after` and that exact key. A continuation reports partial coverage, including
on the last page. This is a historical metadata index: it can include expired
candidates and does not verify source eligibility or signed deadlines. Listing
works after revocation and starts no worker or model.

Select one complete `pending.` key for native review:

```sh
ipse knowledge review pending.COPY_THE_64_CHARACTER_ID --cwd /path/to/project
```

If the original conversation used a custom sessions directory, add
`--state-dir /path/to/original/sessions`. A copy cannot replace the original
source. Acceptance requires currently active publication permission, sufficient
saved allowance, and the supported Linux protected-storage profile described
above. Provider overrides, `--yes` and `--json` cannot confirm a decision.
Close the original source Session first; the standalone command cannot borrow
its source while another active owner retains it.

Keep the printed `Knowledge reservation` and `Management journal` IDs. Read the
complete historical candidate, source provenance, category and proposed
accepted-decision retention. Enter the fresh `accept CODE` at `approval>`;
anything else cancels. The pending deadline limits when acceptance can occur.
The accepted decision's category age starts at confirmation, subject to the
saved policy expiry and any earlier lineage limits. Acceptance records your
decision; it does not prove the source's premises or authorize other effects.

Display and publication independently check the original source, current
permission and unchanged signed target. A source or permission change after
display can therefore refuse publication. A confirmed success removes the pending row and stores an
accepted decision with its original proof and immutable acceptance link.
A successful result prints `accepted_note_key`; keep that complete `note.` key
for later management, including [forgetting](#forget-a-selected-native-note).
Operation inspection also reports this intended key. The key alone does not
prove that publication completed or that the decision is currently eligible;
check the separate journal/control status and actual target.
A repeated attempt cannot accept it twice. An error or lost reply requires
inspection before new work:

```sh
ipse knowledge operation MANAGEMENT_JOURNAL_ID --cwd /path/to/project
ipse knowledge operation RESERVATION_ID --cwd /path/to/project
```

Inspection does not replay or settle anything. The reservation ID remains useful
if interruption occurred before a journal was created. Confirmed acceptance
charges one operation with measured input/output bytes; cancellation and known
pre-publication refusal settle zero effect usage. An uncertain attempt retains
its reservation. Review can also take a bounded explicit selection as described
below. After confirmed acceptance, follow the bounded current-note recall procedure
below. A saved acceptance alone does not prove successful later recall.

### Review selected proposals together

Choose two to eight complete keys from the historical list:

```sh
ipse knowledge review pending.FIRST_64_CHARACTER_ID pending.SECOND_64_CHARACTER_ID --cwd /path/to/project
```

Use the same project/home, saved configuration and original Sessions directory
as single-candidate review. Add `--state-dir /path/to/original/sessions` when
needed. Duplicate keys, more than eight items and an immutable manifest over
8 KiB refuse before a review reservation. Split a larger selection into separate
commands. Provider overrides, `--yes`, `--json` and piped acceptance are refused.

Keep the printed batch/manifest identity and each reservation/journal ID. Each
native prompt displays the complete frozen manifest: exact selected texts,
record hashes/revisions, source classes and provenance, signed pending deadlines
and proposed accepted retention. It also displays the current candidate's full
source proof and highlights its position. Read the current item, then enter its
fresh `accept CODE`. Every item needs separate fresh input. Selecting keys in the
command does not accept any of them, and there is no unseen accept-all action.

Each publication independently rechecks its exact record, source, exclusions,
installed selection and active permission. A changed selected candidate refuses
instead of silently rebuilding the manifest. Cancellation, refusal or an uncertain
outcome stops the rest of the batch. Earlier confirmed items remain saved; other
items keep their original pending expiry. There is no rollback or automatic replay.
List remaining pending keys and start a new review when ready.

Each confirmed item charges its own measured operation. Inspect each printed
journal/reservation ID after interruption with `knowledge operation ID`. An
acceptance journal reports its manifest hash, batch ID, zero-based item index and
count; these identify the original selection and do not prove current source
eligibility. A partial batch needs per-item inspection rather than an assumption
that the whole selection succeeded. This source/native path remains experimental;
installed, human and annual-workload qualification are separate.

### Leave a proposal for later

Choose a key from the historical list and run:

```sh
ipse knowledge defer pending.COPY_THE_64_CHARACTER_ID --cwd /path/to/project
```

This checks that exact stored proposal and its signed expiry, then reports it
as still pending or already expired. Nothing is saved or rescheduled. Its source,
text and original seven-day deadline remain unchanged; deferral cannot renew an
expired item. Repeat the command with `--json` for bounded status output.

Deferral works with capture disabled or permission revoked, and does not need
the original source journal or a terminal. It starts no worker, model request,
management journal or charged operation. To return later, use `knowledge review`
with the same key and complete a fresh native acceptance review. That later
publication independently checks current permission, source and expiry. A
successful deferral report supplies no acceptance or source eligibility.

### Reject one pending candidate

Use the same historical metadata list to select an unwanted proposal, then run:

```sh
ipse knowledge reject pending.COPY_THE_64_CHARACTER_ID --cwd /path/to/project
```

Keep the printed `Management journal` ID. Read the complete selected candidate,
signed metadata and rejection scope, then enter the fresh `reject CODE` at
`approval>`. Anything else cancels. This command requires the same project,
private home, installed bundle, native terminal and supported Linux protected
storage profile. Provider overrides, `--yes` and `--json` are refused. No model
or worker starts, and the original source Session need not be available.
Rejection remains available after capture permission expires or is disabled,
including when the candidate's signed seven-day deadline has elapsed.

A confirmed rejection removes that pending candidate and saves an exact
candidate suppression. It does not reject another proposal or literal note
derived from the same source. The source's original admission clocks and
retention stay unchanged. The same source/text candidate cannot be captured
again; other candidate texts still follow their existing policy and deadlines.
Original journals, shared evidence and earlier delivered answers remain.
Each rejection uses one management operation and retains a suppression record;
this path has no background removal of those records.

If rejection is unconfirmed, inspect `knowledge operation MANAGEMENT_JOURNAL_ID`
and actual stored state before new work. The candidate may already have been
removed; inspection and resume never repeat the effect. Cancellation and stale
codes leave the selected state unchanged. This source-runtime path is
experimental; installed, human and full-workload qualification remain open.

### Edit one pending proposal

Use the complete pending key and your proposed replacement text:

```sh
ipse knowledge correct pending.COPY_THE_64_CHARACTER_ID 'Use ISO dates in the release report.' --cwd /path/to/project
```

This edits text while preserving the displayed category, original source
attribution and signed pending deadline. It requires active capture permission,
the same project/home and supported Linux native terminal/storage profile.
Keep the original source Session journal available; add
`--state-dir /path/to/original/sessions` when it is outside the default directory.
No model or worker runs. Provider overrides, `--yes` and `--json` are refused.
Text is limited to 2,048 UTF-8 bytes and must differ from the selected text.
An oversized review refuses without truncation.

Keep both printed IDs. Read the complete original candidate, replacement text,
storage changes and unchanged expiry, then enter the fresh `correct CODE` at
`approval>`. Anything else cancels. The displayed original is historical data;
publication checks its source version, exclusions, active consent and exact
stored target again. A missing source, revoked consent or changed target can
therefore refuse an edit after its display.

Confirmed success removes the old pending identity, suppresses its exact
source/text candidate and prints `replacement_pending_key`. The replacement
stays pending with its original proof and admission clocks. Original journals,
shared source metadata and other proposals remain. To accept the edited decision,
run `knowledge review` with that new key and complete its separate fresh
`accept CODE` review. The old key cannot be accepted after replacement.

Correction charges one operation with measured input/output; subsequent acceptance
has its own operation. Cancellation and known refusals settle zero effect usage.
An unconfirmed attempt retains its reservation and may already have changed
storage. Inspect `knowledge operation MANAGEMENT_JOURNAL_ID` before new work.
Its `replacement_pending_key` is the intended target, including for an uncertain
attempt; it proves neither presence nor acceptance. Inspection never replays or
settles the attempt. This experimental source path has no installed, human or
annual-workload qualification.

## Correct or supersede a native note

Start interactive chat with the same project, private home and active native
knowledge selection used for the original note. Use the supported protected
Linux storage profile described above. Keep the original Session journal and
its source pages available; closing that conversation is allowed. Obtain the
exact `note.HASH` key from the capture result or a current note lookup.

For an ordinary note, enter:

```text
/correct note.HASH My corrected statement
```

For a current statement or preference, enter:

```text
/supersede note.HASH My new current statement
```

Replace `note.HASH` with the complete key. The first review shows the replacement
statement, its category and scope. Enter its fresh `remember CODE` to endorse
those exact bytes. The second review shows the complete proposed relation,
including the old and new records, source proofs and retention bounds. Wait for
`approval>`, then enter that review's fresh `correct CODE` or `supersede CODE`.
Bare `yes`, an earlier code or any other text does not confirm the relation.
These are separate one-attempt reviews; saved permission and `--yes` cannot
replace them. Headless correction and supersession remain unavailable.

The statement is limited to 1 KiB. An oversized review refuses rather than
truncating its facts. Display locks release before the second answer; the
publication rechecks permission, the original sources and the exact selected
collection root afterward. A changed or missing source, revoked permission or
stale target can therefore refuse a previously displayed proposal. The input
wait is bounded to 120 seconds, followed by a 30-second effect permit without
renewal.

A confirmed replacement becomes current while the original journal and record
remain historical evidence. It does not erase earlier answers or transcripts.
A pinned target keeps its persistent signed historical support after temporal
replacement; forgetting the successor does not erase that history. Later use
still checks current permission and original sources.
If an attempt reports an unconfirmed result, inspect the Session journal and
current note state using the [recovery guidance](recovery.md) before another
attempt: the replacement may already have happened. Resume makes no retry and
does not restore either review's permission. These source controls do not qualify
installed, human or live-model workflows, or replacement of accepted decisions.

## Use bounded current-note recall

Use the same project, home and reviewed selection. After a decision card returns
to its resumed chat, you can ask a followup there; a new chat can also retrieve
stored notes. Ask a question that uses one of the saved facts or preferences.
Before the first model request of each turn,
the native selection prepares a turn-local Reference from current authenticated
notes without another model service. Notes remain attributed derived evidence;
recall does not promote them to new operator statements.

Accepted decisions retain their recorded user-decision attribution and original
source; acceptance does not establish that the source's premises are true.
They can join the bounded pass on the supported Linux native path. Each read and
later use checks the signed record, immutable acceptance link, original committed
management journal, original Session source and current permission. Worker
delivery checks the selected records and final collection root again while
retaining both original journals through its native write and settlement.
Keep both journals available; missing or changed originals withhold the decision
text. The registered provider route remains required for managed context; the
credential-free demo does not qualify this delivery path. A later ordinary tool
proposal uses the separate native `allow CODE` review described above; accepting
the decision itself supplies no tool permission.

The automatic pass reads metadata pages and whole current notes within its
context and host-resource limits. If all notes read so far fit, it can continue
past the first 32 candidates. When the set does not fit, it tries to consider
the first 32 eligible notes before choosing whole notes for the available space;
host limits can stop it sooner.
The pass reports partial coverage when it stops early, omits notes or encounters
an unavailable original. On Linux, a confirmed missing original Session journal
can be skipped while later notes are checked. A protected single-note read can
also confirm that a literal's signed ordinary retention deadline has elapsed;
the pass skips its text and continues to later notes with partial coverage.
This neither deletes the stored record nor renews its lifetime. Other source,
ownership or permission failures withhold the pass when the cause cannot be
established safely. Missing or expired source text is never supplied.

Inspect coverage and use the declared index/read tools for further pages rather
than treating an incomplete pass as proof that no note exists. A skipped journal
may reappear before the model request; the pass remains partial and does not
automatically add that note. Start another pass if you need to check it again.
Search examines at most 32 candidates per invocation. It reports partial coverage
for a later cursor, a safely skipped missing original, a record metadata mismatch
or remaining metadata pages. Other source or permission failures and a changed
collection generation withhold the pass as unavailable. Check `unavailable` and
`next`, and inspect earlier pages as well when searching the whole collection.
A practical prompt is: “Use the knowledge index tool to list the next page, then
read the note with this exact key: `note.<64-hex-character-key>`.” Replace the
placeholder with a returned key and ask the model to follow the returned cursor
when another page is needed. These are model tools, not slash commands.
A search made only of
whitespace or punctuation is refused; provide at least one search term. If recall
or search reports `invalid_index_progress`, it stopped on an inconsistent metadata
page, continuation or count. Inspect the collection and recovery guidance before
retrying; the interrupted pass does not establish complete coverage. Pending
proposals do not become current merely by being recalled.

If an automatic index call fails, the pass discards its earlier keys and reports
unavailable coverage. A deliberate stop at a context or resource bound instead
retains its selected results and reports partial coverage. A null candidate count
means the number is unknown; it does not mean the collection is empty.
If a current read or the final index check observes a different collection
generation, recall or search also withholds that pass and reports unavailable
coverage. Start a new pass to inspect the current collection. These checks do
not lock the collection for the entire pass; a later change still requires
current-use revalidation.

The selected main model can still look up this conversation's sources and propose
a new capture after recall. Earlier notes keep their original attribution and
source requirements. A confirmed new capture can make earlier index metadata
historical; Ipse adds a notice and checks the recalled records again before
continuing. The new pending proposal supplies no substitute for those records'
original sources. If a source becomes unavailable or permission is revoked after
publication, the proposal may already be saved even though the turn stops before
its next result is delivered. Inspect the Session journal and pending metadata
before deciding on new work. Resume does not retry the capture or its delivery.

This integration remains experimental: installed journeys, retrieval quality,
cache behavior and latency are not yet qualified. The tested later-turn withdrawal
path covers ordinary native Ollama text with closed, host-validated provenance.
If changed or forgotten notes remain inside an unsupported opaque provider
continuation, the next request refuses instead of silently rewriting that
continuation. Start a fresh session after the change. No provider is substituted
automatically. Forgetting also preserves original journals and already delivered
answers; it does not erase those historical copies.

## Forget a selected native note

From the original project and Ipse home, use the complete `note.` key followed
by its 64 lowercase hexadecimal characters. The key can select a native literal
or an accepted decision:

```sh
ipse knowledge forget note.COPY_THE_64_CHARACTER_LINEAGE --cwd /path/to/project
```

Use a matching native input/display terminal and the saved configuration. The
current development source supports this on Linux only when the protected
storage locations satisfy the [allocation profile](arch-linux.md#check-protected-storage-admission).
The project identity, management control and selected bundled artifact must be
available. No model or worker is started. Headless use, provider overrides,
`--yes` and `--json` are refused; `--yes` cannot replace this review.

The command first prints `Management journal: ID`. Keep that ID, then read the
complete displayed target, signed metadata, proposed action and scope. Enter
the exact `forget CODE` at the `approval>` prompt, using the fresh code in that
display. Any other answer cancels. The review describes the stored target even
if its signed deadline has elapsed, capture permission was revoked, or its
original source is unavailable. It does not establish that source's current
eligibility or authorize another use of its text. Ipse checks the target and
management state again before applying the confirmed action.

On confirmed success, the selected note is removed and signed suppression
remains; the command prints the settled operation receipt. For an accepted
decision, its immutable acceptance link also remains, preventing the original
card from being accepted again. Original Session and acceptance/management
review journals and shared evidence remain. Previously delivered
answers are not recalled or erased. If the command reports an unconfirmed
result, or it stops before reporting one, inspect the printed journal ID before
another attempt:

```sh
ipse knowledge operation MANAGEMENT_JOURNAL_ID --cwd /path/to/project
```

This inspection does not replay or reconcile the operation. An incomplete
forgetting or retention journal tail makes the journal result unconfirmed even
if an earlier result is present; the separately reported control status may
still be settled.
A `publishing`, unconfirmed or missing result may follow an admitted action that completed
after its review expired or its owner was lost. Inspect the actual storage
outcome and follow [protected recovery](recovery.md#inspect-unconfirmed-protected-knowledge)
before deciding what to do next. A matching installed package and non-Linux
behavior have not yet been qualified for this path.

## Change a selected native note's retention

Choose a retention policy for a selected stored literal or accepted decision on
a supported Linux native terminal. Session-only removes the selected note through
its separate native forget review. For example:

```sh
ipse knowledge retention note.COPY_THE_64_CHARACTER_LINEAGE --policy session --cwd /path/to/project
ipse knowledge retention note.COPY_THE_64_CHARACTER_LINEAGE --policy pin --cwd /path/to/project
ipse knowledge retention note.COPY_THE_64_CHARACTER_LINEAGE --policy automatic --cwd /path/to/project
ipse knowledge retention note.COPY_THE_64_CHARACTER_LINEAGE --policy duration --days 30 --cwd /path/to/project
```

Review the complete facts and type the displayed policy-specific confirmation.
Session-only uses `forget` and the same protected removal and suppression as
explicit forgetting; it does not erase the original journal, management review
journal or shared evidence. Pin has no selected expiry; automatic selects 90 days,
and duration selects the positive number of days provided. The finite choice
starts at native confirmation; the original admission clock remains recorded.
For an accepted decision, the public record and immutable acceptance link also
stay unchanged. Its recorded category and original deadline describe acceptance;
the authenticated native retention choice supplies its effective lifetime. A fresh
read must check that choice before recall or later use. Retention does not change
the decision's original attribution, endorse its premises or grant other effects.
An expired target cannot be extended by a new persistent choice. Existing signed
choices remain readable, and dependencies cannot borrow another revision's
deadline. Inspect uncertain operations with
`knowledge operation JOURNAL_ID` before deciding what to do next; they are not
automatically replayed.

## Reclaim an expired native note

After a signed finite retention deadline has elapsed, reclaim its stored literal
or accepted decision with the exact note key:

```sh
ipse knowledge expire note.COPY_THE_64_CHARACTER_LINEAGE --cwd /path/to/project
```

Replace the complete placeholder with the actual key. The command displays the
full target and its elapsed signed policy, then performs that policy's reclamation.
It uses the already saved retention choice, without a new per-record confirmation.
It requires a normal interactive native terminal and respects execution ceilings
and explicit effect denial. Headless use, provider overrides, `--yes` and `--json`
are refused.

An already expired ordinary policy, finite historical retention or accepted-decision
deadline qualifies. An accepted decision's signed deadline can be shorter than
its category's age limit because acceptance is also bounded by the saved policy.
An accepted decision with no finite deadline refuses reclamation. Its immutable
acceptance link and original admission clocks remain after removal; the original
pending card cannot be accepted again.
Persistent literal pins, current statements and preferences remain stored; an explicit
finite retention choice on one of those statements can later qualify. Reclamation
preserves original admission clocks and, for history, its signed successor link;
it advances the old-backup floor and leaves other notes and shared evidence in
place. A historical retention choice may be compacted in signed storage after
its exact reviewed capsule has been saved in the reclamation journal; a signed
commitment remains to authenticate that capsule. Reading or
recapturing the same expired support cannot give it a new
lifetime. Capture permission may be disabled or expired, and the original source
may be unavailable.

The original Session and management journals remain, including reviewed target
text. No model or worker runs. Preserve the printed management journal ID and use
`knowledge operation JOURNAL_ID` to inspect an unconfirmed result before retrying.
There is no idle background collector or automatic replay of an uncertain attempt.
Management requires a matching native helper before it creates its journal.
An unavailable helper or an unsafe management directory refuses; rebuild or
restore the matching installation and preserve existing files for inspection.
Do not repair an unsafe directory by deleting locks or changing its contents.
A journal containing only a header does not establish that reclamation ran.

## Inspect readiness or the saved review

```sh
ipse knowledge status --cwd /path/to/project --json
ipse knowledge permissions --cwd /path/to/project
```

Status distinguishes a matching saved selection from broad capture readiness.
`activation_ready_now` checks the current installed artifact, route and timeout.
The conservative `publication_supported_now` flag still reports strict publication
support as false, and `capture_ready_now` requires both a matching selection and
that support. The narrower new-v3 admission scope is not represented as full
support by these fields:

```json
{"publication_supported_now":false,"capture_ready_now":false,"publication_unavailable_reason":"collection_deadline_fence_unavailable"}
```

An `activation_ready_now` value of true can therefore coexist with false full
capture readiness. Plain status describes the limited native-reviewed statement
path and the remaining broad saving limitation. The saved permission remains
intact. Status also reports
whether this worktree is admitted, the policy digest, epoch, expiry and headless
selection.
It does not join a worktree, create a project or reclaim staged files. An
unadmitted folder can still join during new-session admission when a repository
grant permits it. Readiness is an observation; every later effect checks current
permission again.

`permissions` prints the complete saved policy without attempting activation.
Its `activation_ready_now` is null; it still reports false strict publication
support and full capture readiness.
Use it when status refuses after a changed route or unavailable artifact.
Neither command starts a worker or inference.
Keep saved output private because it describes your project and selected routes.

Changing provider configuration does not silently replace the route in an old
permission. Review `knowledge enable` again under the intended saved configuration,
then start a new session. An existing conversation retains its pinned catalog;
it cannot adopt the replacement selection in place.

## Revoke future effects

```sh
ipse knowledge disable --cwd /path/to/project
ipse knowledge status --cwd /path/to/project
```

Enter the fresh `disable CODE` after reviewing the project and epoch. Revocation
preserves stored records, operation receipts and unresolved liabilities. It stops
later knowledge effects; already admitted work may have started. New sessions
use the ordinary catalog. Existing sessions retain their saved artifact identity
and must pass the live permission check before another effect.

If setup reports a consent conflict, inspect permissions and perform a fresh
review. A concurrent permission change is never overwritten by the older review.
Changing the saved configuration during review also refuses the save, even when
the edited file would select equivalent settings. Inspect it and begin a fresh
review so the displayed selection matches the configuration being admitted.
If an outcome is unconfirmed, follow [protected knowledge recovery](recovery.md#inspect-unconfirmed-protected-knowledge) before retrying; a
missing confirmation is not proof that nothing changed. Unsafe private-directory
permissions, a missing retained `.lock` or `.writer.lock`, or malformed protected
data refuse rather than being repaired by status. Preserve the original state
for diagnosis.
